## 2. Git và commit — không đưa WIP thẳng lên main

1. `Mobile main` ở official local checkout có thể đang **lùi 9 commit**; dùng personal Mobile worktree `foxonworld/booking-mobile-serviceorder-20260922` HEAD `6a640f6` dựa trên origin/main mốc audit. **62 file staged/unstaged/untracked** là nhiều slice có phụ thuộc chéo; lưu trạng thái trước bất kỳ git operation. Tuyệt đối không `git add .`, không force-push/rebase/reset/stash trên dirty worktree, không xóa file đồng đội hoặc đưa personal AgentMemory/handoff/config vào shared repo.
2. **Bước đầu:** tạo commit riêng cho **tài liệu audit/task board**, không đưa hàng chục source chưa được cross-slice review vào commit tài liệu. Trạng thái code hiện tại test Jest 762/762 PASS, typecheck/Expo PASS, targeted 12-file ESLint PASS, full lint FAIL 4 old resolver errors; các test này không thay cho cumulative code review. Nếu owner yêu cầu checkpoint code cục bộ sau khi diff audit xong, gom exact paths có kiểm soát và ghi `WIP source checkpoint / NOT PR-ready` rõ ràng; một checkpoint lớn **không** là phương án PR cuối.
3. Để chia commit có thể review được, giữ dependency order: `API contracts + test + dev adapters`; `Customer Booking create/matching/history`; `Tech invitations/jobs`; `Shared ServiceOrder detail/read controllers`; `Tech check-in/evidence/quote/start/cost/after/completion`; `Customer quote/cost decisions`; `integration/navigation/tests`. Khi một file chung (`orders.api.ts`, `AppNavigator.tsx`, detail screen) chứa nhiều slice, chỉ dùng `git add -p`/exact hunk sau khi kiểm diff và test **mỗi commit ở trạng thái source nhất quán**; nếu không tách an toàn thì làm một local source checkpoint rồi review để chia qua PR sau. **Không giả định mỗi commit chạy được chỉ vì head worktree PASS.**
4. Sau cumulative review của **tất cả** code (bao gồm source mới untracked, code team, privacy/role, ambiguous POST, error UI), chạy `npm test -- --runInBand`, `npm run typecheck`, `npm run check:expo`, scoped ESLint, `git diff --check`, native/E2E theo task. Ghi chính xác full lint FAIL/pass và file owner. Khi source freeze & review pass mới xin phép push **personal feature branch**, tạo PR sang `dev` để team review. `dev`→`main` chỉ leader xử lý sau UAT; không tự merge/deploy.
5. Team member có thể làm **audit/UI contract/test plan** song song ngay, nhưng implementation cho `CustomerOrderDetailScreen.tsx`, `TechnicianOrderDetailScreen.tsx`, `AppNavigator.tsx`, `orders.api.ts` phải serialize qua integrator/file lock; tách branch/worktree sạch *sau khi* người nhận đã có commit code tương ứng, không copy 62 dirty files sang team repo.

## 3. Một testcase E2E xuyên suốt (khi môi trường sẵn sàng)

- T01 Customer login → catalog serviceId thật → địa chỉ/phường hợp lệ → một Booking hợp lệ, future arrival; ảnh Booking nếu đã có private-upload contract. `SUBMITTED` không có ServiceOrder.

- T03 Khi ACCEPT thực, Customer/Tech history/detail đều mở đúng `serviceOrderId`; Tech EN_ROUTE, GPS VALID, BEFORE upload/get signed media; quote nếu INSPECTION_REQUIRED, Customer Approve/Reject theo testcase; startRepair → UNDER_REPAIR.
- T04 Tech AFTER, resolve pending additional costs, bấm request-completion **một lần trên dev**; invoice UNPAID, completionRequestedAt tồn tại, **chưa COMPLETED**. Customer xem AFTER/invoice → confirm once; invoice vẫn UNPAID trừ khi provider/cash được xác minh riêng.
- T05 Finance/Provider owner mới cho phép test payment verified/actual cash confirmation theo route thích hợp. Chỉ khi BE xác nhận cả confirm và PAID mới `COMPLETED`, warranty/review/history đúng; không tự sửa DB sang PAID hay click mock hoàn thành.
